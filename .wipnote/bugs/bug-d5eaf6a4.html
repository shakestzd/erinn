Description

cmd/wipnote/reindex.go reindexEdges globs only tracks, features, bugs and spikes — never plans. Plan IDs are also never added to validIDs, so indexNodeEdges target-validity gate drops edges POINTING at a plan even when scanned correctly from the source. Empirically confirmed on an isolated clone: plan-f8c02547.html carries two relates_to edges in its nav data-graph-edges block, byte-for-byte present on disk, and a full reindex of unchanged HTML produced zero. Affects contains, blocks, blocked_by, relates_to and implemented_in whenever the source is a plan. The write side is correct — PlanCollection.AddEdge dual-writes properly. The defect is entirely on the read side. Note the fix must add the plans dir AND register plan IDs as valid targets together, or feature to planned_in to plan edges scanned from the feature side break instead.
