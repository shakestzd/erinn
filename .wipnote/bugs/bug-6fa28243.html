Description

Refiled after the prune --catch-up attempt in feat-2bd74c58 was removed on review. THE GAP: the ndjson sweep only archives a session the telemetry indexer has fully consumed, and .index-offset is advanced by exactly one thing, the indexer started inside wipnote serve. A user who never opens the dashboard accumulates telemetry forever with retention silently gated off. Measured growth on this repo during multi-agent work: about 176k lines and 141MB per hour. WHY THE OBVIOUS FIX IS WRONG: running the same indexer from wipnote prune advances the marker, but post-cutover the indexer destination is a throwaway in-memory projection that prune closes on return, so the marker would certify consumed when nothing durable consumed anything. retention.Sweep then writes a tar.gz and removes the live session directory, converting a fail-closed interlock into fail-open. Three further defects showed up in that attempt and any retry must avoid them: the flag was not gated on --dry-run so a preview mutated markers and armed the next real prune to delete; a fresh Indexer resumes at offset 0 and republishes markers downward capped at 4MiB per tick, so prune reclaimed nothing and left markers worse than it found them; and an idle-window exit measured total bytes consumed, which never stalls while a session is appending, so prune blocked for its full 10 minute deadline. SUGGESTED DIRECTION: the marker currently conflates two facts, bytes read and data durably captured. Post-cutover only the first is achievable, so retention should gate on a separate marker that means safe to archive, or recognise that archiving is lossless via tar.gz plus session restore and drop the ingestion gate entirely. Both are design decisions rather than performance fixes.
