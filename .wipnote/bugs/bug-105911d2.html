Codex OTel signals carry no session_id and are discarded wholesale at ingest

Description

MEASURED on the live corpus. A Codex session running tonight wrote 132,116 telemetry lines to its canonical NDJSON shard. 131,109 of them - 99.2 percent - have session_id set to the empty string, and every one is discarded by the writer, which begins its per-signal loop with: if s.SessionID == "" { continue }. Codex telemetry is being collected and durably stored, and then thrown away at the SQLite boundary, silently. Only Codex is affected. Every other shard in the corpus has zero sessionless signals; this one shard accounts for all of them, and every sessionless line carries harness "codex" with resource attrs service.name=codex_cli_rs, service.version=0.147.0. The discarded signals are not noise. Top native names by volume: span/receiving 32,997, span/handle_responses 32,993, span/append_items 29,966, span/persist_rollout_items 14,981, span/auth 1,750, span/send_raw_response_items 857. Sample canonical values include api_request with duration_ms populated, so these are real request-level spans, not internal chatter. A second defect is visible in the same lines and should be checked while fixing this: ts is "1970-01-01T00:00:00Z" on the sampled records, i.e. epoch zero rather than a real timestamp. That does not cause the drop (nothing filters on ts_micros) but it would make any signal that did land sort to the beginning of time and corrupt every time-bucketed dashboard query. Verify whether the timestamp is missing at the source or lost in the adapter. The drop is correct behaviour given the data - otel_signals.session_id is NOT NULL with a foreign key to sessions, so a sessionless row cannot be stored - which means the fix belongs upstream in the Codex adapter or in whatever populates session context for Codex OTLP exports, not in the writer. Worth confirming whether Codex emits a session identifier under a different attribute name that the adapter is not reading, since it clearly knows which conversation it is in. Relationship to existing work: bug-ba376a49 (done) improved Codex OTel fidelity - native names, typed field promotion - and closed with the note "Remaining validation should compare a fresh Codex session against Claude OTel in the dashboard/API." This is that comparison, and the answer is that the rows never arrive at all, so the fidelity work is currently unobservable in the dashboard. bug-3e4c6e02 covers Codex exec-mode not creating a wipnote session, which is adjacent but distinct: this is about the session_id field on signals that ARE being exported. Found while measuring the bug-0fc17d53 recovery replay: the sessionless population had to be subtracted from the expected post-fix row count, which is what surfaced it.
