RESEARCH-ONLY. Adopt-vs-build survey for three approved-but-unbuilt designs, requested by team-lead. Searched web, GitHub (gh api star/push signals), and pkg.go.dev — not vendor docs alone. === TARGET 1 — Durable append-only claim ledger (feat-21d12cdb) === Design: git-tracked NDJSON log, one record per claim lifecycle event, ingested into derived SQLite by existing reindex path. Candidates rejected: - hallgren/eventsourcing (281 stars, active) — embedded Go event-sourcing lib, but backs onto a pluggable EventStore (bbolt/sql/memory), i.e. a binary or server-backed store. Fails "git-diffable, survives fresh clone" — binary formats produce meaningless git diffs and aggregate/merge semantics don't match a plain append log. - altairsix/eventsource, thefabric-io/eventsourcing — DynamoDB/Postgres-backed. Require a running server; violates "no server" and "survive fresh clone" constraints outright. - tidwall/wal, hashicorp raft-wal style segmented WALs — binary, optimized for throughput not diffability. Same rejection as above. - immudb (9,015 stars, pushed within days, very active, embeddable-as-library mode exists) — closest in spirit (cryptographically verifiable immutable ledger with time-travel queries) but stores state as its own binary/merkle-tree files, not text. Not git-diffable; a fresh `git clone` gets file bytes but immudb's format isn't designed to be inspected or merged as text, and it's an entire embedded database engine for what is fundamentally a small structured log — disproportionate. - NDJSON wrapper packages on pkg.go.dev (evandrolg/ndjson, adotkp/ndjson, prologic/jsonlines, go.mills.io/jsonlines) — checked pkg.go.dev importers: evandrolg/ndjson has ZERO dependents. These are single-author shims around `encoding/json` + `bufio.Scanner`/`bufio.Writer`, each under ~100 lines. Adopting one trades an import + version-pin liability for what stdlib already does directly; not a meaningful reuse win. Conclusion: BUILD. The hard constraint (git-tracked, human-diffable, survives fresh clone with zero runtime/server) rules out every event-store/event-sourcing library found — they all assume they own a binary or server-backed storage engine, which is the opposite of what's wanted. This is not "event sourcing" in the library sense; it's a plain text log format, and Go stdlib (encoding/json line-by-line + bufio.Scanner) is the correct-sized tool. This also matches wipnote's own established pattern (AGENTS.md: ".wipnote/*.html — canonical store," git-tracked human-readable artifacts as source of truth) — the claim ledger should follow the same convention already proven in this codebase, not import a new one. === TARGET 2 — Upstream attribute drift detection (bug-735806ff) === Problem: adapter tests assert against synthetic spans; real harness output drifted (tool_use_id empty on ~39,700 rows, present in attrs_json on half) undetected by a green suite. Candidates evaluated: - Pact / pact-go (951 stars, pushed yesterday, very actively maintained, real production tool) — REJECTED on fit, not maturity. Consumer-driven contract testing requires a cooperating PROVIDER side that runs verification against the pact broker. wipnote's "provider" is Anthropic/OpenAI/Google's CLI harness output format — none of those vendors will run Pact provider verification against wipnote's contracts. Architecturally this is a one-sided relationship (wipnote only consumes), which is exactly the shape Pact is not built for. - Golden/approval testing on real captures — gotest.tools/v3/golden (577★ parent repo, but this subpackage last published Sep 2024 — stable/idle, not abandoned) and bradleyjkemp/cupaloy/v2 (330★, last push May 2023, 17 known importers) — both viable, well-understood Go snapshot-testing libraries. Lightweight: capture real adapter output once, diff future captures against the committed golden file, CI fails loudly on any shape change including silent renames. This directly targets the root cause (tests built on synthetic input) at low adoption cost. - JSON Schema validation of captured payloads — no dedicated Go tooling found beyond hand-rolling with a JSON Schema library (e.g. santhosh-tekuri/jsonschema); doable but is really "golden testing with an extra layer," not a distinct category worth a separate dependency. - **OpenTelemetry Weaver** (open-telemetry/weaver, official OTel org project, 461★, pushed 2026-08-07, releases every 1-2 weeks) — ships a **live-check** mode: "Check the conformance level of an OTLP stream against a semantic convention registry," validated against REAL emitted telemetry, not synthetic fixtures. Registries are user-authorable YAML, not limited to the public OTel semconv set — wipnote can define its own registry of required attributes per harness adapter (tool_use_id etc.) and run live-check against captured/replayed payloads in CI via the existing weaver-live-check-start/stop GitHub Actions. This is the OTel ecosystem's own answer to "does anything validate emitted attributes against a convention registry against real traffic" — yes. Caveat: pre-1.0, breaking changes between minors (pin version); requires payloads to be OTLP-shaped, so if wipnote's captured adapter output isn't already OTLP when it hits this check, a translation step is needed first. Conclusion: ADOPT, layered. Immediate/cheapest fix: replace synthetic-span fixtures with golden/approval tests captured from real harness sessions (cupaloy or gotest.tools/golden — either is fine, both are thin and stable) — this alone would have caught the tool_use_id bug, since a real capture would show the field populated where the golden file expects it. For the durable, systemic answer ("fails loudly whenever upstream renames a field, not just when someone remembers to refresh a golden file"), adopt OTel Weaver live-check with a wipnote-authored semantic convention registry, run in CI against periodically-refreshed real captures. Do not adopt Pact — wrong shape for a one-sided, uncooperative upstream. === TARGET 3 — The lineage model itself === Question: should wipnote's edge vocabulary (caused_by, implements, part_of, blocks) align with an existing standard rather than diverge from it? - **OpenLineage** (2,587★, pushed today; latest release 1.52.0 on 2026-07-23, monthly cadence, core Run/Job/Dataset model has been stable for years with growth happening additively via the facet extension mechanism — NOT churning like gen_ai) — Run/Job/Dataset/Facets model. Fetched the object-model spec directly: it assumes directional dataset I/O ("most Jobs have at least one input or output Dataset"), scheduled/repeatable job semantics (cron-style recurrence distinguishing Runs of the same Job), and execution-lifecycle states (START/COMPLETE) rather than development lifecycle states (opened/claimed/reviewed/merged). Real production adopters confirmed: native integrations in Airflow/Spark/dbt/Flink/Dagster (15+ platforms), consumed by Datadog/Atlan/DataHub/OpenMetadata/IBM watsonx/AWS MWAA, named enterprise users (Northwestern Mutual, BMW Group). So this is NOT a maturity or adoption problem — it is mature, stable, and genuinely production-proven, in its own domain. The rejection is a confirmed domain mismatch (data-pipeline runs, not dev work items), not a stability concern. POOR FIT stands, on stronger grounds than before. - **W3C PROV / PROV-O** (Entity/Activity/Agent; wasGeneratedBy/wasDerivedFrom/wasAttributedTo/wasAssociatedWith/wasInformedBy/actedOnBehalfOf) — Status check: became a W3C Recommendation in April 2013, working group closed the same year, and it has NOT been revised or superseded since — the spec is genuinely frozen/stable, unlike gen_ai's active churn. But adoption is real, not theoretical: NIST's CASE digital-forensics standard maps onto PROV-O, ProvLake/PROV-ML use it for ML-pipeline provenance, and multiple scientific-workflow/data-curation tools implement it — however every real implementation found is in scientific/data-provenance/semantic-web communities, not mainstream software-engineering or DevOps tooling. No git host, issue tracker, or CI system uses PROV-O as its lineage model. Correcting my earlier framing: this means adopting PROV vocabulary would NOT buy "legibility to people who already know it" in the way OpenTelemetry vocabulary would for observability engineers — PROV's fluent audience is provenance researchers, not the software engineers who'll read wipnote's code. That claim doesn't survive scrutiny and I'm retracting it. What DOES survive scrutiny is the structural fit, checked relation-by-relation against wipnote's actual claim-ledger problem (feat-21d12cdb: "which agent held which work item at time T"): - `wasAssociatedWith` (Activity↔Agent, "this agent carried out this activity") is the precise match for the claim-holding relationship itself — a claim is naturally a time-bounded Activity (prov:startedAtTime = claimed, prov:endedAtTime = released/completed/abandoned/expired) associated with an Agent. This is a better fit than `wasAttributedTo` for the core "who held it during [t1,t2]" question, because wasAttributedTo relates a finished Entity to an Agent with no time window — it answers "who produced this," not "who was holding this when." - `wasAttributedTo` (Entity↔Agent) is still the right relation for the complementary question — "this commit/artifact is attributed to this agent" — after the fact, once the entity exists. - `actedOnBehalfOf` (Agent↔Agent) fits parent/child agent-spawn delegation directly. Net: the vocabulary fit is real and precise, not just superficially plausible — but the "adopt for legibility" argument is weak given PROV's actual (non-software-engineering) user base. The honest case for alignment is "free, precise, already-solved naming for a graph we're building anyway," not "converging with what other dev tools do" (nothing comparable does). - **SLSA / in-toto** (slsa-github-generator 591★, in-toto/attestation 361★, in-toto-golang 151★, all pushed within days — actively maintained, real production use in supply-chain security) — model builder/materials/invocation/predicate for cryptographically-signed (DSSE) supply-chain attestation. Different threat model: built for a THIRD PARTY to verify an artifact they don't trust; wipnote's lineage is first-party observability of its own agents, no adversarial trust boundary. Mature and well-adopted, still a poor fit — adopting DSSE signing/verification for internal lineage would be unjustified overhead. Naming analogy only (builder.id ~ wipnote's agent-attribution need). - **PROV-AGENT** (arXiv 2508.02866, DOE/UT-Battelle, 2025) — extends W3C PROV specifically for LLM-agent workflows (MCP + telemetry into one provenance graph). Corroborates that PROV-alignment is the right instinct for exactly this attribution problem — but it's a research paper with no widely-used reference implementation, i.e. it's evidence for the vocabulary choice, not itself an adoptable thing. - OpenTelemetry GenAI semantic conventions — per the parallel doc audit: `gen_ai.system`/`gen_ai.request.model`/`gen_ai.tool.call.id` are Deprecated in the main registry, moved to a separate still-in-Development `semantic-conventions-genai` repo, with `gen_ai.system`→`gen_ai.provider.name` renamed; no `gen_ai` convention for success/outcome exists at all (OTel's answer there is span status ERROR + `error.type`, which the harness doesn't use). This is the clearest case in the whole survey of "a standard exists" being insufficient grounds to align — it churns faster than the vendor attribute it would replace. Confirms the general principle applied above to OpenLineage and PROV: check current spec status, stability guarantee, and real implementers before aligning, not just "is there a standard with this shape." Conclusion: ALIGN vocabulary with W3C PROV, don't adopt any tooling. No drop-in standard models wipnote's specific graph (dev work items + git commits + coding sessions + agent spawn trees). OpenLineage is disqualified on domain fit despite being mature and widely production-adopted in its own domain — a clean "real standard, wrong problem" case. PROV is disqualified as a source of "everyone will recognize this" legibility (its production users are provenance researchers, not software engineers) but its relation vocabulary — specifically `wasAssociatedWith` for time-bounded claim-holding, `wasAttributedTo` for after-the-fact artifact attribution, `actedOnBehalfOf` for agent-spawn delegation — maps precisely onto wipnote's actual open problems (feat-21d12cdb's claim ledger, bug-735806ff's per-signal attribution) and costs nothing to borrow since only the naming/documentation is being adopted, not PROV-O's RDF/OWL/triple-store machinery. Recommend: annotate wipnote's edge-type definitions with their PROV-relation equivalent as documentation, and consider using `wasAssociatedWith`-style (time-bounded activity/agent) framing rather than a flat attribution field when designing feat-21d12cdb's ledger schema. SLSA/in-toto is mature and well-adopted but solves a different problem (third-party trust vs. first-party lineage) and isn't worth adopting. gen_ai semconv is the standing cautionary example: don't align with something that churns faster than what it replaces.
