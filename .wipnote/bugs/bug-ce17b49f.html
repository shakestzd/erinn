Artifact autocommit hard-fails on transient git index.lock (IDE/gitstatus daemon), re-opening completed work items

Description

commitWipnoteArtifact and commitWipnoteArtifactStrict (cmd/wipnote/workitem_commit.go) run 'git add'/'git commit' and fail immediately on ANY error, including a transient "Unable to create .git/index.lock: File exists / Another git process seems to be running". That lock is routinely held for a fraction of a second by a git-status daemon (gitstatusd), IDE, or concurrent git ls-files. On the strict path this re-opens the just-completed work item and forces a manual 'rm .git/index.lock' + retry (hit 3+ times in one session). Fix: wrap the git add/commit invocations in a bounded retry-with-backoff that retries ONLY on the index-lock contention signature (mirror the existing internal/db RetryOnBusy/DefaultBusyBackoff pattern: ~200/600/1800ms). Real failures (hook rejection, permission denied, nothing-to-commit) must still fail/return fast — only lock contention is retried. Do NOT auto-delete the lock (could be a genuine concurrent git); just wait and retry. Affects any user with a git daemon/IDE running, so the fix belongs in the binary.
