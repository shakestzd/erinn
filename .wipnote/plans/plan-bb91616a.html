Problem

wipnote's SQLite read index is written concurrently by multiple short-lived processes — dashboard (serve_child), hook subprocesses (dbgate), and 13 direct CLI mutation sites (openDB). This multi-writer topology causes recurring SQLITE_BUSY failures masked (not eliminated) by RetryOnBusy, and a real unsynchronized race between reindex checkpoint-reset (reindex_otel_events.go:46/140) and the live indexer. Meanwhile the dashboard mostly broad-polls JSON (and polls SQLite every 2s for plan feedback via planEventsHandler at api_plans.go:942), divergence/failure conditions surface only as opaque counters, and the canonical-vs-derived contract lives only in a test inventory.

Goals

  1. Make a single per-project daemon (graduated serve_child) the sole owner of SQLite writes, eliminating SQLITE_BUSY structurally rather than via retry.
  2. Keep .wipnote/*.html + events.ndjson canonical and SQLite explicitly rebuildable-derived, with staleness visible to operators.
  3. Replace broad dashboard polling with named snapshot+delta SSE projections that reconnect-resume.
  4. Promote conflicts, stale indexes, failed/spooled hook writes, and duplicate-agent activity to first-class, resolvable dashboard objects.

Constraints

  • Canonical artifacts are the source of truth; a writer must never block or lose a mutation because the daemon is unreachable (auto-spawn primary, spool last-resort).
  • Direct canonical cutover with NO config flag and NO shadow mode (single dogfooding user today); soak test + reindex-race fix are the safety net.
  • Reindex must remain a foreground command honoring the existing TMPDIR-safety contract — never backgrounded on volatile tmpfs.
  • OUT OF SCOPE: WASM boundary, DuckDB replacement, CRDT rewrite, required cloud sync. No new runtime dependency beyond the existing go.mod.

#1 Write-op protocol + Unix-socket listener over the serve_child writqueue Define a transport-agnostic write-op envelope and expose the existing M Med Complex Pending 3 issues 1 Q
What

Define a transport-agnostic write-op envelope and expose the existing serve_child writqueue (internal/db/writequeue: Queue + WriteOp, op.go:46, queue.go:83 — in-process-only today) over a per-project Unix domain socket in .wipnote/. The single-writer writqueue already exists inside serve_child but is only reachable in-process. Exposing it over a stable local socket is the precondition for every other writer (hooks, CLI, reindex) to route writes through one owner instead of opening SQLite directly — the structural fix for SQLITE_BUSY (research doc, Item 3).

#2 Daemon lifecycle: headless writer-only serve_child, on-demand auto-spawn, single-owner lease Graduate servechild into an on-demand writer daemon. L High Complex Pending 3 issues 1 Q
What

Graduate serve_child into an on-demand writer daemon. FIRST build a headless writer-only mode in serve_child: today serve_child always binds HTTP (serve_child.go: only a --port flag) — add a mode/flag that skips HTTP setup and runs only the socket listener + writqueue. The existing spawn path (os.Executable + exec.Command via the supervisor, serve.go:204) couples the child to an HTTP handshake (child prints port, parent scans stdout); the headless path must break that handshake cleanly (signal readiness via socket dial, not stdout port). A writer discovers the socket; if absent/stale it auto-spawns the headless daemon and blocks until ready (bounded readiness wait). Enforce single-owner via an O_EXCL PID/lease file so two writers racing to spawn converge on one daemon (loser dials the winner). Idle-timeout shutdown is guarded by a connect-grace so a writer dialing during shutdown re-spawns on a stale PID rather than failing.

Why

For the daemon to be the canonical writer with no config flag (locked decision), ANY writer must be able to guarantee a daemon exists. Auto-spawn makes "is the daemon up?" a non-question. The lease prevents the multi-process double-spawn race the current intentionalCLIMutation paths would otherwise create.

State: O_EXCL PID + lease file in .wipnote/; readiness = first successful socket dial after lease validation (NOT stdout port scan). Payload: none new — reuses slice-1 envelope once connected. Rejected: standalone always-on wipnote daemon process (second lifecycle, larger build) — graduating serve_child reuses the existing writqueue + doorway with least new code; library-mode opportunistic leadership (trickiest handoff semantics).

#3 Spool last-resort fallback + durable drain-on-start with persistent dedup Add the last-resort path for the rare case where auto-spawn itself fails M Med Complex Pending 2 issues 1 Q
What

Add the last-resort path for the rare case where auto-spawn itself fails (e.g. a hook in a sandbox that cannot fork). The writer writes the canonical artifact first, then appends the write-op envelope to an append-only spool under .wipnote/spool/ using atomic-append + fsync + a per-record length/CRC framing so a crash mid-write leaves a truncatable (not corrupting) tail. On next start the daemon drains the spool in order, submitting each op through the durable dedup marker (slice 1) so replay is safe and convergent even if a crash occurred after apply but before spool-entry removal. A corrupt tail record is logged as an anomaly (slice 10) and truncated, never blocking the drain. Spool entries are removed only after an applied/duplicate ack.

Why

The locked decision is "auto-spawn primary, spool only as last resort." The canonical .html is always the source of truth, so a writer must never block or lose a mutation just because it could not reach/start the daemon. The spool guarantees the derived index eventually converges without making the daemon a hard dependency (research doc, absolute-availability ethos).

Decisions

Trigger: spool append happens ONLY on auto-spawn failure (last resort), not on every write. State: append-only spool files in .wipnote/spool/ with length+CRC framing and fsync; canonical .html written before spooling; a durable last-applied marker (shared with slice 1) is the dedup source of truth across restarts. Payload: the slice-1 versioned envelope (with op_id) is what gets spooled and later submitted. Durability: atomic-append + fsync + per-record CRC so a crash mid-write yields a truncatable tail; corrupt tail -> anomaly + truncate, never a permanent drain block. Rejected: spool-always (Stage-2 default) — superseded by auto-spawn-primary; direct-DB-with-retry fallback — reintroduces the multi-writer contention this plan removes; in-memory-only dedup — loses state on restart (double-apply risk).

#6 Coordinate reindex through the daemon (close the checkpoint race, no self-deadlock) Make wipnote reindex a daemon-coordinated operation. M Med Complex Pending 2 issues 1 Q
What

Make wipnote reindex a daemon-coordinated operation. Today reindex resets .index-offset checkpoints (reindex_otel_events.go:46) and removes them (line 140) while a running indexer may be advancing them — an unsynchronized race (confirmed: no lock today). Route reindex through the daemon so checkpoint-reset and indexer-advance cannot interleave. Critically, reindex runs AS a daemon operation (submitted to / executed by the writqueue owner), not as an external process grabbing the same lease the daemon's consumer holds — this avoids self-deadlock. Spool drain and reindex both run inside the daemon's single write context, serialized by the consumer, never competing for a lock. Lease/coordination acquisition has a bounded timeout that returns a clear error rather than hanging. Preserve the foreground + TMPDIR-safety contract (never background reindex on volatile tmpfs).

Why

Reindex resets .index-offset checkpoints while a live indexer may advance them — an unsynchronized race that can lose or duplicate offset progress. Serializing reindex inside the daemon's single write context closes a known correctness gap the single-owner model otherwise exposes, without introducing a reindex-vs-daemon self-deadlock.

Build the reactive projection layer by generalizing the planEventsHandler pattern (api_plans.go:919 — 2s ticker at 942, lastRowID high-water at 936/940, text/event-stream). Define a projection registry keyed by stable names (active-work, session-events:, lineage:, agent-activity, collector-status, plan:). Each projection serves an SSE channel whose first event is a full snapshot carrying a monotonic seq, followed by delta events with increasing seq; clients reconnect with Last-Event-ID to resume. Define a compaction/retention policy (keep last N events or T window per projection); if a client's requested seq is below the compaction floor, send a fresh snapshot instead of deltas. Seq space: use the slice-1 writer monotonic seq when the daemon is present; otherwise a per-projection counter in a clearly namespaced space so the two never collide. Ship infra + active-work end to end.

Why

Most dashboard panels do broad JSON polling today; the only streaming is a 2-second SQLite poll ticker. Named snapshot+delta projections cut read-pool pressure and make the UI live (research doc, Item 4).

Files
internal/projection/registry.go, internal/projection/sse.go, cmd/wipnote/api_projections.go, cmd/wipnote/serve_child.go
Done when
  • Opening a projection SSE channel yields a full snapshot with a monotonic seq, then deltas with increasing seq
  • Reconnecting with Last-Event-ID resumes from the client's last seq without a full re-snapshot
  • Reconnecting with a seq below the compaction floor receives a fresh snapshot (defined fallback), not an error
  • The active-work projection drives a dashboard panel without polling /api/initial-stats
Decisions

Trigger: GET /api/projections/ as text/event-stream. State: projection state derived read-only from SQLite; seq = the slice-1 writer monotonic seq when the daemon is present, else a namespaced per-projection counter (never overlapping the daemon seq space). Payload: event 1 = {type: snapshot, seq, data}; event N = {type: delta, seq, ops}. Compaction: retain last N events / T window per projection; below the floor -> fresh snapshot (explicit, tested fallback). Rejected: versioned-snapshot-push without deltas (coarse, large payloads); delta-only client reducers (hardest reconnect story).

#10 Anomalies as first-class objects: canonical event + derived table + dashboard panel Promote conflicts, stale indexes, failed/spooled hook writes, and M Med Complex Pending 3 issues 1 Q
What

Promote conflicts, stale indexes, failed/spooled hook writes, and duplicate-agent activity from opaque counters to first-class, navigable objects. The daemon (and reindex/db-health) emit anomaly records into the canonical events.ndjson append-only log; the NDJSON indexer — extended in this slice (reindex_otel_events.go today only parses OTel signals) — projects them into a derived anomalies table that rebuilds cleanly on reindex. A dashboard anomalies panel, driven by a named projection from slice-8, lists open anomalies with timestamp, kind, source, and a resolved/acknowledged state. Duplicate-agent detection source: the sessions/agent-activity table — "active" = a session with in-progress status whose last-update is within a liveness window AND that has claimed/started a given work item; two such overlapping on one feat/bug/spike id raises one anomaly.

Why

The research doc treats divergence as expected in local-first systems and wants it surfaced as resolvable objects, not silent counters. Today fallback and busy counters exist only as numbers in /api/collector-status with no actionable UX (research doc, Item 6).

Files
internal/anomaly/detector.go, internal/anomaly/index.go, cmd/wipnote/reindex_otel_events.go, cmd/wipnote/api_projections.go, plugin/static/dashboard
Done when
  • Spool-used, failed-submit, stale-index, and duplicate-agent events are written to canonical events.ndjson with a defined {kind, source, ts, detail, status} schema
  • The NDJSON indexer recognizes anomaly records and the derived `anomalies` table rebuilds cleanly on reindex
  • Duplicate-agent detection queries the sessions/agent-activity table with an explicit 'active' definition (in-progress + liveness window + claimed work item)
  • A dashboard anomalies panel lists open anomalies with kind, source, timestamp, and an ack/resolve action
Decisions

Trigger: daemon/reindex/db-health emit an anomaly event when a divergence condition is detected. State: CANONICAL events.ndjson record (survives rebuild) + derived anomalies table (rebuildable) — chosen over derived-only (ephemeral) or per-anomaly .html (heaviest). Indexer: reindex_otel_events.go is extended to recognize a new anomaly record type alongside OTel signals (the critic flagged this as previously unowned). Payload: {kind: conflict|stale_index|failed_hook_write|duplicate_agent, source, ts, detail, status: open|acked|resolved}. source is kind-specific: hook event id for failed/spooled writes; the two session ids + work-item id for duplicate_agent; table name for stale_index. Duplicate-agent "active": sessions/agent-activity row with in-progress status, last-update within a liveness window, and a claimed/started work item; overlap on one id = anomaly. Rejected: derived-only anomalies table (lost on reindex, not local-first); dedicated .wipnote/anomalies/*.html (heaviest — revisit only if anomalies need full lineage/linking).
