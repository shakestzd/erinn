Adapter tests use synthetic spans, so upstream attribute drift is undetectable

Todo High Priority

Caused By:

  • otel success column not persisted on tool_result/tool_execution/api_request spans

Part Of:

  • trk-c4615ad2

Relates To:

  • tool_use_id column populated on zero rows while attrs_json carries it on half
  • Agent identity acquisition must be a per-harness seam, not a Claude-specific path

Description

The tests covering harness signal conversion assert against spans the tests themselves construct. They therefore pass regardless of what the harness actually emits, which means a renamed or removed upstream attribute causes silent data loss with a fully green suite. This is not hypothetical: the success derivation fix reads an attribute found empirically in captured traffic, with no documented contract confirming the name, and the tool_use_id column is already populated on zero rows while the same value sits in attrs_json on about half of them — an existing instance of exactly this failure mode that went unnoticed for the life of the table. The project's own guidance states these schemas drift silently and that a prior audit found silent-failure drift across all shipped harnesses. Needed is a mechanism that observes real traffic rather than synthetic fixtures: a density assertion over recent rows, a canary that fails when a field's population rate falls below a threshold, or a periodic contract check against captured samples. Whatever the mechanism, the requirement is that a field going missing upstream produces a loud failure rather than a quiet column of NULLs.
