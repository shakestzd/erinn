Pinned SQLite driver embeds an engine with the WAL-reset corruption bug

Todo High Priority

Part Of:

  • trk-2c55adea

Description

The pure-Go driver is pinned at a release embedding SQLite 3.49.2, verified directly in the module cache. Upstream carried a write-ahead-log reset race from 3.7.0 through 3.51.2, fixed in 3.51.3: when two or more connections write and checkpoint the same WAL-mode database concurrently, the file can be corrupted. wipnote defaults to WAL and its normal operating mode is many concurrent agent processes writing the same index — the exact trigger shape, and busy contention from that pattern was observed repeatedly today. Bumping to the current release moves the engine to 3.53.3, well past the fix, and was verified green: no breaking API changes across the range, and build, vet, test, a triple stress pass and a race run all clean across every module in a scratch clone, with a baseline comparison showing no divergence. Note the minimum release carrying the virtual-table subpackage embeds 3.51.2 and is still inside the bug window, so the smaller-looking jump would leave the defect in place. Severity is tempered by the index being derived: corruption costs a rebuild rather than data loss. One side effect to check before landing — the dependency graph raises the language directive, so confirm build runners can fetch the newer toolchain.
