Telemetry tables grow unbounded — no retention reaches SQLite rows, about 66MB per month

Todo High Priority

Part Of:

  • trk-2c55adea

Description

otel_signals, agent_events, messages and tool_calls have no age or TTL based deletion anywhere. Measured over a 31-day window: otel_signals grows about 1196 rows/day at roughly 1510 bytes/row, or 54MB/month; agent_events about 8.4MB/month; messages and tool_calls about 3.4MB/month. Total near 66MB/month unbounded, extrapolating to roughly 800MB/year for a local-first tool. Telemetry is 80 percent of the current 86MB file (otel_signals alone 65.4 percent, dominated by attrs_json averaging 740 bytes/row). The retention concept already exists — observe/otel/retention defines a 30-day default — but it only archives on-disk events.ndjson files and never touches DB rows. The only cap in the writer applies to metric-kind rows at 5000 per session, leaving log and span rows uncapped. Extend the existing retention mechanism to the telemetry tables. Note this is an 80 percent problem with a small fix, and worth doing before any larger question about replacing SQLite.
