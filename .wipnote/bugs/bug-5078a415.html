OTLP http/json decode expects hex trace and span IDs but protojson emits base64

Todo Medium Priority

Part Of:

  • trk-c4615ad2

Description

Building a real captured fixture surfaced this: the decode path's comment states trace and span identifiers are hex-encoded per an OTLP JSON spec deviation, but the OTLP proto library ships no custom JSON codec for those fields, so the standard protobuf-JSON decoder treats them as base64. A hex string therefore decodes to the wrong byte count and the identifier validity check silently drops the span — zero spans decoded, no error. Real Claude Code traffic is unaffected because the harness registry hardcodes the protobuf protocol, where identifiers are raw bytes with no encoding ambiguity. But the receiver accepts JSON, so any traffic arriving that way would lose spans silently, and the comment actively documents behaviour the library does not have — which is worse than no comment, because it would send the next investigator the wrong direction. Two things to settle: whether the JSON ingestion path should decode base64 as the library actually produces, and correcting the comment either way.
