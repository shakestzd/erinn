Description

A full reindex on identical data was measured at roughly 15 minutes and 47.5 minutes on two clean runs. The variance is structural, not noise. The otel stage accounts for 66 percent of the fast run and the entire difference between the two: 9 minutes 53 seconds versus 42 minutes 37 seconds on the same corpus. Root cause is the indexer's drain-until-two-consecutive-stable-ticks convergence loop racing live traffic. Other agents' sessions append to their own event logs continuously while the loop runs, so it keeps finding new bytes in files it does not own the writer for, and it terminates only when the machine happens to go quiet. Reindex duration is therefore a function of how busy the system is, with no bound. Recommended direction: snapshot each session's byte offset when the loop starts and drain only up to that mark, so a reindex covers a defined point in time rather than chasing a moving tail. A second, independent cost sits in the same stage: the batch write path loops over signals writing one at a time despite its name, which is a real cost on a corpus of roughly 89 thousand lines and is separate from the termination problem.
