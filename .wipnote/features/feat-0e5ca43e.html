Description

Gate records are the last decision-affecting data in wipnote with no canonical source. Seventy-five rows across forty-one work items exist only in the derived index, which lives in the operating-system cache directory and may be purged at any time — while the completion gate consults them through a fallback window to decide whether a work item may complete. A purge silently changes whether completions are permitted, and nothing can rebuild them. They are also structurally ideal for the ledger pattern proven twice already: one immutable row per gate run, keyed by work item, queried by recency, with no open-close lifecycle since a gate run is a completed fact when written. STORAGE: a git-tracked HTML table under the store following the architecture-cards and claim-ledger precedent, fragment-addressable by record id, reusing the shared file-lock write path and the deferred commit queue. Consult the claim ledger's sharding decision and follow or diverge deliberately; gate runs are far rarer than claim events so a single file is plausible. The index table becomes a derived read cache rebuilt by reindex like every other canonical artifact. TWO DECISIONS SETTLED DURING SCOPING, both reversing an earlier framing. First, the allowlist hit detail DOES belong in the canonical row. An allowlist hit is not decoration — a gate command that failed is converted to a pass when its failure matches an allowlist entry, so the hit record is the reason a failure was forgiven. Only the count is consumed today, in session adherence reporting, but the detail names which entries were hit, which is what makes it possible to ask later whether a pass was forgiven for a reason since fixed, or whether an allowlist has gone stale. Dropping it would make every historical pass indistinguishable from a clean one, permanently. Second, the completion gate SHOULD read the ledger directly rather than the index. No counter-argument survived scrutiny: the parse is trivial on a command that runs at completion time, and independence from index state is the goal rather than an inconsistency. One real consequence to accept knowingly — gate decisions become coupled to working-tree git state, so checking out an older commit surfaces that commit's records. That is judged correct semantics, since a gate record is a fact about a tree state, but it is a behaviour change and should be documented. This is what makes the gate-reproducibility bug resolvable rather than perpetually worked around. Acceptance Criteria Gate records survive a cache wipe and a fresh clone. The completion gate reads canonical, so a purged index does not change whether a completion is permitted. Allowlist hit detail is preserved canonically. The index rebuilds from the ledger.
