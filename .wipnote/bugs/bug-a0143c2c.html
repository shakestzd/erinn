success is read from a beta span attribute when a non-beta source exists

Todo Medium Priority

Caused By:

  • otel success column not persisted on tool_result/tool_execution/api_request spans

Part Of:

  • trk-c4615ad2

Relates To:

  • Adapter tests use synthetic spans, so upstream attribute drift is undetectable

Description

The shipped success derivation reads the success boolean from claude_code.llm_request and claude_code.tool.execution spans. Doc audit confirms the attribute name and type are documented exactly as used, so the fix is correct — but those spans live under the Traces feature, which is explicitly beta and carries a documented warning that span names and attributes may change between releases. That is a stated instability, not a hypothetical one. A non-beta equivalent exists for tool outcomes: the claude_code.tool_result log event is part of the standard log signal, is not gated behind the beta flag, and carries both success as a string and tool_use_id. Prefer that source for tool outcomes, or read both and cross-validate so a divergence surfaces as a signal rather than silently picking a loser. No non-beta path exists for llm_request success — that field is beta-only, making it the single highest-risk input in the current derivation, and it should be marked as such wherever it is consumed.
