Migration replay test breaks whenever a new migration lands on top of it

Todo Medium Priority

Part Of:

  • trk-2c55adea

Description

A receiver test rewinds the schema version to current-minus-one, drops a column added by that step, and expects the replay to restore it. That assumption holds only while the step in question IS the newest one. A later, unrelated migration landing on top makes current-minus-one replay the new step instead, so the dropped column is never restored and the test fails — with a message that points at the receiver rather than at the migration that moved beneath it. Observed immediately when a second ledger added its own step. This is the same brittleness class as a test that hardcodes line numbers: it asserts a position in a sequence rather than the behaviour it means to check. Re-anchor it on the specific migration step by name or version constant rather than on a relative offset from the current head, so it keeps testing that a pending migration is applied on writer construction regardless of what else has been added since.
