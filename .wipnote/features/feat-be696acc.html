Description

feat-82e11bbb shipped work-item attribution on OTel rows using a hardcoded agent_id of __root__, and explicitly documented subagent-level attribution as a follow-up that was never filed. The consequence is now measured: the writer resolves feature_id from active_work_items for (session_id, __root__), and SetActiveWorkItem is INSERT OR REPLACE, so a session has exactly one mutable claim slot. In a multi-agent session every subagent signal is stamped with whatever the root claimed at that instant. Verified live: a session running roughly 40 named parallel subagents holds one active_work_items row, so all of their telemetry attributes to a single work item. Adjacent claim windows were observed overlapping by about 97 seconds. This produces confidently wrong numbers rather than visibly missing ones, which is worse than sparsity, and it is the normal orchestration pattern for this project. Lead hypothesis to test first: otel_signals already has parent_span, and subagent_invocation is an existing canonical kind, so the span tree may already encode which subagent emitted a signal without needing a new agent_id field. Walk parent_span up to the nearest subagent_invocation and attribute from there. Second requirement: active_work_items is current-state-only, so there is no historical claim log to recompute attribution retroactively. Making claims append-only with timestamps is what would make any backfill correct rather than inheriting the same error.
