Description

cmd/wipnote/reindex_trailers.go line 23 runs git log with a hard -500 limit, so git_commits.feature_id and everything downstream (reindexFeatureFiles) only ever sees the 500 most recent commits. Measured on an isolated clone: a full reindex as shipped links 122 of 457 test files (26.7%), which is actually WORSE than the live DB floor of 139. Parsing the full 5179-commit history with the exact same parenWorkItemRe regex, just without the cap, reaches 393 of 457 test files (86.0%) and 351 referenced work items. Loosening the regex to also match bare non-parenthesized IDs reaches 413 (90.4%). 90.7% of all commits already self-identify a work item; the code simply does not read past 500. Raising or removing the cap is close to a one-line change and unlocks retroactive linkage across the whole corpus with no new tables and no human curation.
