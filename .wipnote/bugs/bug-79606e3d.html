Description

The success column on otel_signals is populated on 461 of 39476 rows (1.2 percent), but it is semantically defined on nearly all of them. Breakdown from the live index: tool_result 332 of 7033, tool_execution 125 of 6352, api_request 3 of 7103. Every tool result is either a success or an error, so this is a writer bug, not sparse-by-design. The plumbing works when it fires — populated rows split 327 success and 134 failure — so the column and its readers are fine; the common write path simply drops it. This blocks per-work-item failure rate, which was the headline fact the rollup feature exists to produce. By contrast duration_ms is dense where applicable (api_request 100 percent, tool_result 98.8, tool_execution 94.6) and attempt is 90 percent on api_request, so those facts are viable today. Investigate the receiver write path that maps harness-native spans onto these canonical kinds.
