Concurrent agents on one working tree make the completion gate unreliable

Todo High Priority

Part Of:

  • trk-2c55adea

Description

Work item completion re-runs the quality gate, but in a multi-agent session every agent shares one working tree and one derived index. Observed live with three agents mid-edit: a completion attempt reported a build failure in the root package that did not exist moments later — the gate had simply sampled a half-written tree — and two consecutive attempts failed to record a gate result at all with database is locked, SQLITE_BUSY, because the single-writer index was contended by roughly thirty concurrent agents. Both symptoms come from the same cause and neither indicates a real defect in the work being completed. Consequences: agents cannot complete their own work items and either give up or force past the gate with allow-dirty, which is exactly the escape hatch the gate exists to prevent. This also means a red gate in a shared tree carries no information, which erodes the gate generally. Options worth weighing: isolate agents in worktrees so each gates its own tree, make gate-record insertion retry on lock contention rather than failing, or decouple completion bookkeeping from gate execution so a committed and linked change can be completed without re-running a suite that another agent is concurrently invalidating.
