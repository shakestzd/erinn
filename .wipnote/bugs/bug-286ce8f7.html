OTel agent_id schema migration gated behind serve; writer swallows resulting write errors

Done High Priority

Part Of:

  • trk-c4615ad2

Description

Original filing: bug-6f0f0b3a (team-lead, not visible in this session's index/worktree -- see completion note for the sync gap). The otel_signals.agent_id column (feat-be696acc) is added via an idempotent ALTER embedded inside CreateOtelTables, which core/db/migrations.go only calls from step version 1 (stepCreateBaseTables). Once a database's PRAGMA user_version reaches currentSchemaVersion, runMigrations short-circuits and step 1 never runs again -- so any DB that was already fully migrated before this ALTER was added to source never receives the column, regardless of which binary or which entry point (serve, hooks, reindex) opens it afterward. Confirmed live: this repo's dev DB has user_version=18, feature_id present, agent_id absent. Separately, observe/otel/receiver.NewWriter (own-pool mode, used by cmd/wipnote/reindex_otel_events.go) opens its DB handle via a raw sql.Open and never runs migrations at all, unlike NewWriterFromDB's callers which pass in an already-migrated handle from dbpkg.Open. Both gaps combine to make agent_id silently NULL on every signal, with the resulting per-row/per-batch SQL errors logged-and-continued (never surfaced as a single actionable failure) by observe/otel/indexer.RunOnce and cmd/wipnote/reindexOtelEvents. Fix: (1) promote the otel_signals attribution columns into a properly versioned migration step so they apply to any already-migrated DB; (2) make receiver.NewWriter run migrations like every other writable-open path; (3) verify the otel_signals schema once at Writer construction and fail loudly and immediately if a column the INSERT depends on is missing, instead of deferring to repeated per-row failures.
