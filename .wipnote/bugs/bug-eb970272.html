Launch chooser omits current session: session-split children lose work-item attribution

Todo Medium Priority

Relates To:

  • CLI-first resume chooser and continuation hydration redesign

Part Of:

  • trk-6a1f5362

Description

Symptom: the styled launch chooser (wipnote claude --dev) does not list the user's CURRENT session on main. Root cause (verified): the resumable-session query ListHarnessGroupedResumableSessions in core/db/session_repo.go filters at line 705 with 'WHERE sw.work_item_id <> ''' — only sessions carrying a work item are shown. Claude Code splits a session internally: the SessionStart hook fires on the short parent stub (which gets active_feature_id), but the real long-running child session IDs never receive a SessionStart the hook sees, so their active_feature_id / active_work_items are never written and work_item_id resolves to '' — eliminated at :705 before any other filter. Secondary: the parent stub's work item can be completed, hitting the second filter at :728 'item_status NOT IN (done, completed)'. Net: the current main session is structurally absent, not merely ranked low. Two fix paths (both in feat-4f5fafee scope): (1) forward-propagate work-item attribution from the parent stub to its split-child session IDs (fixes the data pipeline; the more correct fix); (2) add a first-class 'current session' slot in the chooser (cmd/wipnote/claude_chooser.go listGroupedResumableSessionsForRoot) that bypasses the work_item_id gate. Anchors: core/db/session_repo.go:705 and :728; cmd/wipnote/claude_chooser.go. NOT a regression from the trk-6a1f5362 restyle merge — pre-existing data-pipeline gap.
