Tests opening :memory: without pinning the pool can silently see an empty database

Todo Medium Priority

Part Of:

  • trk-08dcbb33

Description

core/db.Open(":memory:") returns a handle whose pool may open more than one connection, and SQLite gives every new connection to :memory: its OWN private empty database. A test touching the handle from more than one goroutine can therefore have its write land on one database and its read on another; the read simply sees nothing, with no error. TestStartRecapsReindexLoop_PopulatesTableAtStartup hit this and failed roughly one run in four on unmodified main (measured 8/30, and 15/30 under load) - bimodal, passing in 60ms or burning its full 10s deadline, because startDrainLoop swallows the drain goroutine's outcome. Fixed there with SetMaxOpenConns(1) plus SetConnMaxLifetime(0), the remedy core/db/dbtest.OpenForTest already documents in detail. About twenty other test files call Open(":memory:") without the pin; they do not flake today only because they are strictly single-goroutine, so the hazard is latent rather than absent. Options: have Open apply the pin itself whenever the DSN is in-memory (no production caller uses :memory:), or migrate callers to dbtest.OpenForTest. Note the documented deadlock caveat - a single connection is unsafe for code that queries inside an open rows loop.
