Description

Claude's plugin model is ephemeral — the launcher passes a plugin directory per launch, so a bare Claude session has no wipnote hooks at all and the availability question does not arise. Codex is structurally different: its plugin system is install-based, with a marketplace registered into user config, so once wipnote is installed every Codex session picks it up including desktop-app sessions started outside any launcher. Verified against the installed CLI: there is no per-launch plugin flag, only marketplace add, plugin add, list and remove, with local paths accepted as a marketplace source. So wipnote's Codex integration is inherently global in a way its Claude integration is not, and that is a property of the harness rather than an accident of wipnote's implementation. Establish what a Codex session should do when hooks fire with no launcher and therefore no guaranteed daemon. Candidates: work without the daemon exactly as today, reading the derived index; auto-spawn a daemon on first hook; or refuse loudly. Weigh them against the decided policy for launcher-started sessions, which is that a bounded retry then a loud report and graceful pause is correct precisely because the launcher made a promise. A session with no launcher was promised nothing, so the same strictness would be wrong. Also determine whether the desktop app honours hooks registered by a marketplace-installed plugin, and whether config overrides passed to the app launch subcommand propagate into its sessions — both are runtime questions the installed binary can answer.
