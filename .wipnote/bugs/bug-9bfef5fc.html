Activity feed endpoint /api/events/feed hangs ~12s, blocks writqueue (unbounded otel_signals scan)

Todo Medium Priority

Part Of:

Description

queryOtelFeedEvents in cmd/wipnote/api_feed.go runs SELECT over otel_signals (238k rows, ~87k matching) ORDER BY ts_micros DESC with NO SQL LIMIT and two correlated subqueries per row (feature_title, session_family_id); the Go handler caps limit only after fetching all rows. Open sql.Rows holds a SHARED lock ~12s; in DELETE journal mode (overlayfs, WAL disabled) this blocks the writqueue BEGIN IMMEDIATE -> recurring commit/begin SQLITE_BUSY every ~5s, and the HTTP request exceeds the client timeout (HTTP 000) so the frontend stays on 'Loading activity'. Fix: push LIMIT ? into SQL (split OR into UNION ALL so the sorted index range is used) and replace per-row correlated subqueries with post-fetch batch IN-lookups. Distinct from bug-cbdb06ca (render-path on /api/events/recent).
