INSERT OR IGNORE on otel_signals still turns constraint violations into silence

Todo Medium Priority

Part Of:

  • trk-2c55adea

Relates To:

  • Derived otel_signals holds 61,611 rows against 154,614 canonical NDJSON lines

Description

The span_id UNIQUE index that dropped 86,758 signals (bug-0fc17d53) is fixed, but the mechanism that made that loss SILENT rather than loud is still in place and still general. The writer inserts with INSERT OR IGNORE, and SQLite applies that conflict resolution to NOT NULL and CHECK violations as well as to the primary key. Any future constraint a signal fails to satisfy - a new CHECK, a column made NOT NULL, another index - is discarded with no error, no log line, and a checkpoint that advances as if the row had been stored. That is exactly how a 56 percent data loss survived unnoticed. The OR IGNORE is load-bearing and must NOT simply be removed. signal_id is the primary key and idempotent replay depends on that silence: reindexOtelEvents documents it, and the bug-0fc17d53 recovery path depends on it harder still, because recovery replays the entire corpus over a table that already holds most of it. Removing it turns recovery into a wall of primary-key errors. The obvious detector was considered and deliberately rejected while fixing bug-0fc17d53. Flagging RowsAffected == 0 fires on nearly every row of a legitimate replay, so it is pure noise, and a warning that fires constantly trains people to ignore it. Telling "already present, expected" apart from "constraint rejected, a bug" needs to know whether the row already exists, which costs an extra query per ignored row on the hot write path. A half-working detector is worse than none, so none was shipped. The work is to separate the two cases cheaply. Options to evaluate rather than assume: replace OR IGNORE with an explicit ON CONFLICT(signal_id) DO NOTHING, which targets only the primary-key conflict and should let NOT NULL and CHECK violations raise - most promising and close to free, but verify against the actual driver rather than the docs; or sample-verify ignored rows instead of every one; or add a test that enumerates every constraint on otel_signals and proves each produces a loud failure, which catches the class without touching the write path.
