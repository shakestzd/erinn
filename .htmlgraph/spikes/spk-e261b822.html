## Problem Subagent tool calls (Bash, Read, Grep, etc.) appear as direct children of the orchestrator UserQuery event instead of being nested under their Task node in the activity feed. ## Data Model for Session Hierarchy ### Tables involved **sessions** table (ddl.py lines 99-135): - session_id TEXT PRIMARY KEY - parent_session_id TEXT (FK → sessions) ← links child session to parent - parent_event_id TEXT (FK → agent_events) ← links child session to the Task event that spawned it - is_subagent BOOLEAN DEFAULT FALSE **agent_events** table (ddl.py lines 33-66): - event_id TEXT PRIMARY KEY - event_type TEXT — can be "task_delegation", "tool_call", "task_completed", etc. - parent_event_id TEXT (FK → agent_events) ← links an event to its parent event - session_id TEXT — which session this event belongs to - status TEXT — "started" / "completed" for task_delegation events - subagent_type TEXT — e.g. "general-purpose", "researcher" - claude_task_id TEXT — Claude Code internal task id **tool_traces** table (ddl.py lines 226-247): - tool_use_id TEXT PRIMARY KEY — UUID from PreToolUse hook - session_id TEXT - parent_tool_use_id TEXT (FK → tool_traces) ← tool-level nesting - status TEXT ### Intended hierarchy UserQuery (agent_events, event_type=UserQuery, session=PARENT) └── task_delegation (agent_events, event_type=task_delegation, session=PARENT, status=started) └── Bash (agent_events, event_type=tool_call, session=SUBAGENT, parent_event_id=task_delegation.event_id) └── Read (agent_events, event_type=tool_call, session=SUBAGENT, parent_event_id=task_delegation.event_id) ### Actual (broken) hierarchy UserQuery (agent_events, session=PARENT) └── Bash (session=SUBAGENT, parent_event_id=UserQuery.event_id) ← WRONG └── Read (session=SUBAGENT, parent_event_id=UserQuery.event_id) ← WRONG task_delegation (session=PARENT, status=started or completed) ← orphaned or wrong parent ## Where Attribution Breaks Down ### Root cause: hook processes are isolated — env vars do not carry over The attribution chain relies on env vars (HTMLGRAPH_PARENT_EVENT, HTMLGRAPH_PARENT_EVENT_FOR_POST) set in pretooluse.py. These ARE set when the orchestrator's PreToolUse hook fires for Task(). However: **Critical fact** (pretooluse.py line 709, comment): > NOTE: env vars don't propagate between hook processes, so this branch is effectively dead code in the real system. Each hook invocation is a separate subprocess. The env vars set by PreToolUse are gone by the time PostToolUse runs, and are never available to the subagent's hooks at all. ### The four attribution methods in track_event (event_tracker.py) **Method 0 — JSONL parentToolUseID** (event_tracker.py lines 1576-1595): Reads ~/.claude/projects/{hash}/{session_id}.jsonl and looks for agent_progress records with a parentToolUseID field. This field appears ONLY when a tool call executes inside a subagent and Claude Code writes it to the transcript. This is the correct method — but it has a critical weakness: it passes hook_session_id (the subagent's Claude Code session_id) to _find_parent_via_jsonl, then looks that session_id's transcript. The transcript found is the SUBAGENT's transcript, not the PARENT's. The parentToolUseID in an agent_progress record in the subagent transcript refers to the Task tool_use_id in the PARENT session's transcript. The DB join in _find_parent_via_jsonl (event_tracker.py lines 900-919) looks up tool_traces JOIN agent_events WHERE event_type='task_delegation' AND status='started'. This join fails if: (a) there is no tool_traces row for the Task tool_use_id, or (b) the task_delegation status has already been set to 'completed' by commit 644ff738's fix. **Method 1 — sessions table lookup** (event_tracker.py lines 1011-1093): Checks if hook_session_id is already in sessions table with is_subagent=1. If so, finds the task_delegation via subagent_type match. This works for subsequent tool calls in the same subagent session after the first call has registered the session. Fails on the FIRST tool call from a subagent because the session has not been registered yet. **Method 3 — unknown session_id** (event_tracker.py lines 1110-1146): If hook_session_id is not in sessions table, assumes it is a subagent and grabs the most recent started task_delegation globally. This is a heuristic — it is not session-specific. With multiple concurrent subagents or when the task_delegation has already been marked completed by 644ff738, it picks wrong or nothing. **Final fallback — UserQuery** (event_tracker.py lines 1902-1904): If no parent_activity_id found, fall back to the most recent UserQuery in the session. This is the broken path — it flattens subagent tool calls to UserQuery level. ### What commit 644ff738 tried to fix and why it made things worse 644ff738 added this logic in the PostToolUse handler for Task/Agent tools (event_tracker.py lines 1969-1999): After recording the Task tool call event, it immediately marks the task_delegation as status='completed'. The intent was to prevent subsequent orchestrator tool calls (Bash, Read after Task() returns) from being mis-attributed to the now-finished task. **Why this breaks Method 0**: When the subagent runs its tool calls, Method 0 looks for a task_delegation with status='started'. But 644ff738 already set the status to 'completed' at PostToolUse time for the Task tool. The Task() PostToolUse fires when the Task CALL is dispatched (before the subagent finishes), but the subagent's tool calls happen AFTER. So by the time the subagent's Bash runs, the task_delegation has status='completed', Method 0's DB join finds nothing, and it falls through to UserQuery. **Why this breaks Method 3**: Same reason — Method 3 also filters AND status='started'. After 644ff738, no started task_delegation exists. ## What Information IS Available in Hooks The following data IS reliably available: 1. **hook_input["session_id"]** — Claude Code provides this in PostToolUse. This is the subagent's unique session_id (a fresh UUID per Task invocation). 2. **The JSONL transcript** — The subagent's transcript at ~/.claude/projects/{hash}/{session_id}.jsonl contains agent_progress records with parentToolUseID that points to the Task tool_use_id in the parent session. 3. **tool_traces.tool_use_id** — The parent Task's tool_use_id is stored in tool_traces during PreToolUse. This is the correct key to correlate parent and child. 4. **sessions.parent_session_id** — After subagent_start.py registers the subagent session, this column correctly links child session → parent session. 5. **The task_delegation event_id** — Stored in agent_events and can be looked up from tool_traces via tool_use_id. ## Proposed Fix Design ### Fix 1: Do not mark task_delegation completed at Task PostToolUse time The 644ff738 fix fires too early. The task_delegation should remain status='started' until the TaskCompleted hook fires (which already handles marking it completed). Remove or guard the early completion at event_tracker.py lines 1972-1999. Risk: orchestrator's own tool calls after Task() might get mis-attributed to the task. Mitigate with the staleness timestamp check already present (task_delegation timestamp must be > current UserQuery timestamp). ### Fix 2: Make Method 0 (JSONL) work even when task_delegation is completed In _find_parent_via_jsonl, change the DB query to remove the AND status='started' filter. Instead, also accept status='completed'. The task_delegation is still the correct parent regardless of status. SQL change in event_tracker.py around line 906: Remove: AND ae.status = 'started' ### Fix 3: Ensure subagent session registration happens before first tool call The session-start hook (session-start.py) should write the subagent's session to the sessions table with parent_session_id populated. If this runs reliably before the first PostToolUse hook, Method 1 will work for all tool calls including the first. This requires the traceparent queue mechanism (write_traceparent_queue in pretooluse.py, lines 84-132) to be reliably consumed by session-start.py. ### Recommended approach Apply Fix 2 (remove status filter in JSONL join) as the primary fix — it is the smallest, most targeted change and does not depend on timing. Also apply Fix 1 (delay task_delegation completion) as defence-in-depth so that Method 3 also works as a fallback. Together: Method 0 finds the task_delegation via parentToolUseID regardless of status. Method 3 finds it via unknown session heuristic while it is still 'started'. Both converge on the correct task_delegation event_id as parent_activity_id. ## Files and Line References - event_tracker.py status filter: lines 906-909 - event_tracker.py early task_delegation completion: lines 1969-1999 - event_tracker.py Method 0 JSONL attribution: lines 1576-1595 - event_tracker.py Method 1 sessions table: lines 1011-1093 - event_tracker.py Method 3 unknown session: lines 1110-1146 - event_tracker.py final UserQuery fallback: lines 1902-1904 - pretooluse.py create_task_parent_event: lines 292-444 - pretooluse.py write_traceparent_queue: lines 84-132 - ddl.py sessions table: lines 99-135 - ddl.py agent_events table: lines 33-66
