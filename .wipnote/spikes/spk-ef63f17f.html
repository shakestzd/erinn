RESEARCH-ONLY. Adopt-vs-build survey for three approved-but-unbuilt designs, requested by team-lead. Searched web, GitHub (gh api star/push signals), and pkg.go.dev — not vendor docs alone. === TARGET 1 — Durable append-only claim ledger (feat-21d12cdb) === Design: git-tracked NDJSON log, one record per claim lifecycle event, ingested into derived SQLite by existing reindex path. Candidates rejected: - hallgren/eventsourcing (281 stars, active) — embedded Go event-sourcing lib, but backs onto a pluggable EventStore (bbolt/sql/memory), i.e. a binary or server-backed store. Fails "git-diffable, survives fresh clone" — binary formats produce meaningless git diffs and aggregate/merge semantics don't match a plain append log. - altairsix/eventsource, thefabric-io/eventsourcing — DynamoDB/Postgres-backed. Require a running server; violates "no server" and "survive fresh clone" constraints outright. - tidwall/wal, hashicorp raft-wal style segmented WALs — binary, optimized for throughput not diffability. Same rejection as above. - immudb (9,015 stars, pushed within days, very active, embeddable-as-library mode exists) — closest in spirit (cryptographically verifiable immutable ledger with time-travel queries) but stores state as its own binary/merkle-tree files, not text. Not git-diffable; a fresh `git clone` gets file bytes but immudb's format isn't designed to be inspected or merged as text, and it's an entire embedded database engine for what is fundamentally a small structured log — disproportionate. - NDJSON wrapper packages on pkg.go.dev (evandrolg/ndjson, adotkp/ndjson, prologic/jsonlines, go.mills.io/jsonlines) — checked pkg.go.dev importers: evandrolg/ndjson has ZERO dependents. These are single-author shims around `encoding/json` + `bufio.Scanner`/`bufio.Writer`, each under ~100 lines. Adopting one trades an import + version-pin liability for what stdlib already does directly; not a meaningful reuse win. Conclusion: BUILD. The hard constraint (git-tracked, human-diffable, survives fresh clone with zero runtime/server) rules out every event-store/event-sourcing library found — they all assume they own a binary or server-backed storage engine, which is the opposite of what's wanted. This is not "event sourcing" in the library sense; it's a plain text log format, and Go stdlib (encoding/json line-by-line + bufio.Scanner) is the correct-sized tool. This also matches wipnote's own established pattern (AGENTS.md: ".wipnote/*.html — canonical store," git-tracked human-readable artifacts as source of truth) — the claim ledger should follow the same convention already proven in this codebase, not import a new one. === TARGET 2 — Upstream attribute drift detection (bug-735806ff) === Problem: adapter tests assert against synthetic spans; real harness output drifted (tool_use_id empty on ~39,700 rows, present in attrs_json on half) undetected by a green suite. Candidates evaluated: - Pact / pact-go (951 stars, pushed yesterday, very actively maintained, real production tool) — REJECTED on fit, not maturity. Consumer-driven contract testing requires a cooperating PROVIDER side that runs verification against the pact broker. wipnote's "provider" is Anthropic/OpenAI/Google's CLI harness output format — none of those vendors will run Pact provider verification against wipnote's contracts. Architecturally this is a one-sided relationship (wipnote only consumes), which is exactly the shape Pact is not built for. - Golden/approval testing on real captures — gotest.tools/v3/golden (577★ parent repo, but this subpackage last published Sep 2024 — stable/idle, not abandoned) and bradleyjkemp/cupaloy/v2 (330★, last push May 2023, 17 known importers) — both viable, well-understood Go snapshot-testing libraries. Lightweight: capture real adapter output once, diff future captures against the committed golden file, CI fails loudly on any shape change including silent renames. This directly targets the root cause (tests built on synthetic input) at low adoption cost. - JSON Schema validation of captured payloads — no dedicated Go tooling found beyond hand-rolling with a JSON Schema library (e.g. santhosh-tekuri/jsonschema); doable but is really "golden testing with an extra layer," not a distinct category worth a separate dependency. - **OpenTelemetry Weaver** (open-telemetry/weaver, official OTel org project, 461★, pushed 2026-08-07, releases every 1-2 weeks) — ships a **live-check** mode: "Check the conformance level of an OTLP stream against a semantic convention registry," validated against REAL emitted telemetry, not synthetic fixtures. Registries are user-authorable YAML, not limited to the public OTel semconv set — wipnote can define its own registry of required attributes per harness adapter (tool_use_id etc.) and run live-check against captured/replayed payloads in CI via the existing weaver-live-check-start/stop GitHub Actions. This is the OTel ecosystem's own answer to "does anything validate emitted attributes against a convention registry against real traffic" — yes. Caveat: pre-1.0, breaking changes between minors (pin version); requires payloads to be OTLP-shaped, so if wipnote's captured adapter output isn't already OTLP when it hits this check, a translation step is needed first. Conclusion: ADOPT, layered. Immediate/cheapest fix: replace synthetic-span fixtures with golden/approval tests captured from real harness sessions (cupaloy or gotest.tools/golden — either is fine, both are thin and stable) — this alone would have caught the tool_use_id bug, since a real capture would show the field populated where the golden file expects it. For the durable, systemic answer ("fails loudly whenever upstream renames a field, not just when someone remembers to refresh a golden file"), adopt OTel Weaver live-check with a wipnote-authored semantic convention registry, run in CI against periodically-refreshed real captures. Do not adopt Pact — wrong shape for a one-sided, uncooperative upstream. === TARGET 3 — The lineage model itself === Question: should wipnote's edge vocabulary (caused_by, implements, part_of, blocks) align with an existing standard rather than diverge from it? - **OpenLineage** (2,587★, pushed today, very active, Linux Foundation AI/Data project) — Run/Job/Dataset/Facets model. Fetched the object-model spec directly: it assumes directional dataset I/O ("most Jobs have at least one input or output Dataset"), scheduled/repeatable job semantics (cron-style recurrence distinguishing Runs of the same Job), and execution-lifecycle states (START/COMPLETE) rather than development lifecycle states (opened/claimed/reviewed/merged). Forcing work items, commits, or agent spawns into Dataset/Job/Run would require real conceptual stretching — it is genuinely a data-pipeline lineage spec, not a general causal-graph spec. POOR FIT, confirmed from the spec text itself, not just intuition. - **W3C PROV** (Entity/Activity/Agent; wasGeneratedBy/wasDerivedFrom/wasAttributedTo/wasInformedBy/actedOnBehalfOf) — conceptually the closest match. Mapping is direct: work item/commit = Entity, coding session = Activity, human/AI agent = Agent, "commit wasGeneratedBy session," "session wasAssociatedWith agent," "child-agent-spawn actedOnBehalfOf parent-agent," "feature wasDerivedFrom spike." Full PROV-O is RDF/OWL and expects a triple store or SPARQL — that machinery is a bad fit for wipnote's SQLite+git architecture. Recommendation is vocabulary alignment only: rename/annotate edge types where they overlap with PROV relations (a compatibility note in docs, e.g. "part_of ~ PROV wasInformedBy," not a schema migration), so wipnote's model is legible to anyone who knows PROV, without adopting RDF tooling. - **SLSA / in-toto** (slsa-github-generator 591★, in-toto/attestation 361★, in-toto-golang 151★, all pushed within days — actively maintained) — model builder/materials/invocation/predicate for supply-chain attestation, cryptographically signed via DSSE envelopes. Different threat model: SLSA/in-toto exist to let a THIRD PARTY verify an artifact they don't trust; wipnote's lineage is first-party observability of its own agents. Adopting DSSE signing and attestation verification for internal lineage would be substantial, unjustified overhead. Useful only as a naming analogy (their "builder.id" concept parallels wipnote's need to attribute a commit to a specific agent/model), not as adoptable tooling. - **PROV-AGENT** (arXiv 2508.02866, DOE/UT-Battelle, 2025) — an academic paper extending W3C PROV specifically for LLM-agent workflows (integrates MCP + telemetry into a unified provenance graph). Validates that PROV-alignment is the right instinct for exactly this problem, but it is a research paper, not a mature adoptable library — no widely-used implementation exists yet. Cite as corroborating prior art, not as something to depend on. - OpenTelemetry GenAI semantic conventions (draft, active OTel effort) — defines span-level attribute vocabulary for individual agent/tool/LLM invocations (invoke_agent, execute_tool spans). Complements but doesn't replace a lineage graph model: it standardizes what a single span looks like, not how work items/commits/sessions connect to each other. Relevant to Target 2's registry-authoring work more than to Target 3's graph model. Conclusion: ALIGN, don't adopt. No drop-in standard models wipnote's specific graph (dev work items + git commits + coding sessions + agent spawn trees). OpenLineage is a confirmed poor fit. W3C PROV's vocabulary is the right conceptual alignment target — cheap (a documentation/naming exercise, optionally a `prov_equivalent` annotation on edge-type definitions) and it buys legibility to anyone who knows the standard, without adopting PROV-O's RDF/triple-store machinery. SLSA/in-toto's attestation model is a different problem (third-party artifact trust vs. first-party lineage) and not worth adopting. Keep building wipnote's typed edges as they are; document the PROV correspondence.
