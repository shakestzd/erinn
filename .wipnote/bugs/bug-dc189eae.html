SUPERSEDED BY bug-286ce8f7 (same defect, filed independently before this ticket's real ID reached me -- team-lead's brief cited a fabricated ID, bug-6f0f0b3a, twice before this one; content below is the corrected record). Fixed in commit 4e5f7d7ca. Two independent root causes, both closed: 1. core/db/otel_schema.go's CreateOtelTables added otel_signals.feature_id and .agent_id via idempotent ALTERs embedded in its own body. CreateOtelTables is reachable only from migration step version 1, which runs exactly once -- the first time a database advances from user_version 0 to current -- never again once a database has reached currentSchemaVersion. This ticket's own prior note ('the versioned migration chain... runs on every database open, and the schema version constant confirms it') was the diagnosis BEFORE realizing step 1 does not re-run on an already-current DB; that is exactly the gap. Fix: promoted both columns into a real versioned step, 019_otel_signals_attribution_columns, and bumped currentSchemaVersion 18 -> 19. 2. observe/otel/receiver.NewWriter (own-pool mode, the constructor cmd/wipnote/reindex_otel_events.go calls for 'wipnote reindex') opened its DB handle via a raw sql.Open and never ran schema migrations at all -- unlike NewWriterFromDB, whose caller (serve_child) passes in a handle dbpkg.Open already migrated. This is the 'two open paths that differ on whether they migrate' this ticket predicted. Fix: added an exported db.RunMigrations and call it in NewWriter before preparing statements. The 'self-resolved 25 minutes later, nothing deliberately run' observation in the original filing was not a mystery: that window was this fix landing and a normal wipnote invocation applying it, not an unexplained recovery. FAIL LOUDLY (this ticket's second acceptance criterion): both Writer constructors now call verifyOtelSignalsSchema once, at construction, which PRAGMA table_info(otel_signals)s and fails immediately and by name if a column the INSERT depends on is missing. Both call sites (reindex_otel_events.go, serve_child.go) already treat a constructor error as fatal, closing the 'hardcoded zero error count' hole this ticket named as the durable part of the defect. Verified non-vacuous by three separate deliberate reversions (each reproduced the exact original failure in a dedicated test, then was reverted) and against this repo's actual shared dev DB post-rebuild, not just isolated fixtures. Full detail in bug-286ce8f7 and commit 4e5f7d7ca's message. Acceptance Criteria Both criteria met: (1) the versioned migration chain now owns otel_signals.feature_id/agent_id as step 019, applied on every db.Open regardless of entry point, confirmed live against this repo's dev DB (user_version=19, agent_id present); (2) both Writer constructors fail once, immediately, by name via verifyOtelSignalsSchema, and both call sites already treat that as fatal -- no more per-batch swallowed errors or hardcoded zero error counts.
