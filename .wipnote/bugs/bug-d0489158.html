Description

reindex_plan_edges.go writes every plan slice's deps entry into graph_edges as relationship_type=blocked_by — the same string a human uses via wipnote link add --rel blocks to assert a genuine cross-project dependency. This runs on every reindex, so it is live. graph bottlenecks (core/graph/pattern.go) then counts to_node_id appearances in blocked_by with zero type distinction, meaning a plan with one foundational slice and seven dependents makes that slice's feature appear as a top-line bottleneck blocking seven work items — when it is only that plan's authoring order. The strategic-planning skill explicitly activates for finding bottlenecks, so this is a path from data conflation to a wrong prioritisation decision, not a hypothetical. Fix by distinguishing plan-internal slice ordering from asserted project dependencies, either via a distinct relationship type or by populating the unused metadata column and filtering on it.
