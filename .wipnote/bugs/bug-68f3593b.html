Description

The canonical HTML write path takes an in-process mutex plus a cross-process file lock on a sidecar lock file, then writes to a temp file and renames. On Windows the lock function returns only the in-process mutex and takes no cross-process lock at all, so two wipnote processes on the same repository can interleave a read-modify-write and silently lose one another's updates. This is the exact failure class that was found real and fixed on Unix — concurrency tests caught genuine lost updates and the fix added the file lock — so the defect is known to be reachable, not theoretical, and Windows simply never received the fix. Impact is probably low today given the project's usage, but it is an unguarded gap in the path any new canonical artifact would reuse, and it should not be inherited silently by new work. Implement an equivalent exclusive lock using the platform's own file locking, and extend the existing concurrency tests to run on that platform rather than assuming the Unix result covers it.
